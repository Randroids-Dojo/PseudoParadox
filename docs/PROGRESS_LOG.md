## 2026-05-10, PR3b Hybrid Replay Using Milestones (F-013 done)

- Branch: `pr3b-hybrid-replay`
- PR: #49
- Changed: Second slice of the four-PR PR3 sequence. Replaces `GhostInstance.advanceTick`'s pure input replay with a hybrid replay state machine driven by the new `src/sim/replayController.ts`. Per the design pass: ghosts replay recorded input by default; if the body's translation drifts more than `DRIFT_THRESHOLD = 0.5` units from the position the recording would produce at the current tick (running expected-position integral), the controller switches to `path-following` mode and steers toward the next pending milestone with `PLAYER_SPEED_MPS`. When the body comes within `ARRIVAL_RADIUS = 0.3` of the milestone, the milestone is marked reached, the milestone index advances, the expected-position baseline is re-anchored to the current body position, and the controller returns to `replaying-input` mode. The skip rule fires per the Q-025 default A: a `wall_bump` whose recorded tick is more than `WALL_BUMP_BUDGET_TICKS = 60` ticks behind the controller's current tick is skipped past; `door_traversal` weight (`DOOR_TRAVERSAL_WEIGHT = 5`) is unskippable. Implementation: pure data plus pure functions. `ReplayState` is a frozen-shape struct (tickIndex, milestoneIdx, expectedPos, lastMode); `advanceReplay(state, recording, milestones, currentBodyPos, fixedStepSeconds)` returns the velocity to write plus the next state. `createReplayState(startPosition)` opens at tick 0, milestone idx 0, expectedPos at startPos, mode `replaying-input`. `GhostInstance.advanceTick` now delegates to `advanceReplay` and stores the next state; `GhostInstance.tickIndex` is mirrored from `replayState.tickIndex` so existing call sites stay unchanged. New field `GhostInstance.replayMode` exposes the most recent mode for debugging. `reset()` rewinds the replay state to its tick-0 starting state alongside the body and consciousness reset; the milestone index returns to 0 so each timeline visit re-walks the milestone sequence from the top. NO change to wireTraversal, milestone capture, or hardReset (PR3a's wiring still drives the milestone log).
- Verification: `npm run type-check` clean. `npm test` 582 passing across 53 suites (was 568 / 52). Em-dash and en-dash sweep clean. `git diff --check` clean. New tests: `tests/sim/replayController.test.ts` adds 14 cases covering the controller's state shape (1), input-mode default path (3), drift-triggered switch (2), milestone arrival semantics (1), skip rule (3), threshold strictness (2 cases pinning that drift exactly at threshold does not switch), and path-follow stickiness (2 cases pinning that once engaged the controller stays in path-follow until the milestone arrival check fires). Existing 568 tests continue to pass because ghosts with `EMPTY_MILESTONE_RECORDING` (Act 1 cinematic actors, ghost test fixtures) stay in input-replay mode forever (the path-follow branch is gated on a pending milestone).
- Assumptions: drift baseline is a running integral of `replayAtTick(recording, t) * fixedStepSeconds` summed over ticks. Does not match Rapier's contact-resolved trajectory exactly (damping is not modeled in the integral), but the threshold is generous enough (0.5 m) that the small physics-vs-pure-velocity discrepancy stays well under the threshold under the prototype's empty-room conditions. The fixed step (1 / 60) is shared via the new `src/sim/simulationStep.ts` module's `FIXED_STEP_SECONDS` export so the host's `fixedStepSeconds` and the replay controller's running integral cannot drift apart. Recording with no milestones keeps the controller in input-replay mode forever. The drift comparison is strict greater-than (`drift > 0.5`); equality stays in input mode. Path-following is sticky: once engaged, the controller keeps steering toward the same pending milestone until the arrival check fires, even if drift drops back under the threshold mid-correction.
